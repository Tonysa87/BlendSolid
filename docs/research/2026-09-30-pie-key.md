# Which key opens the BlendSolid pie (ADR 0013, point 2)

- **Date:** 2026-09-30 (session 12)
- **Question:** ADR 0013 decided a pie on `CLICK_DRAG` of an existing Object Mode key (tap keeps the key's
  action); which key, and does the mechanism work as assumed?
- **Method:** Blender 5.2.2's own keymap generated from `scripts/presets/keyconfig/keymap_data/blender_default.py`
  with the real preference defaults (`Blender.py`: Select with **Left**, Spacebar **Play**), keymaps Window, Screen,
  Frames, User Interface, 3D View Generic, 3D View, Object Mode, Object Non-modal; once with "Pie Menu on Drag"
  off (default) and once on. Add-on keys from their manuals. [verified, source / docs]

## Finding 1 — the mechanism: a `PRESS` binding can't share its key with a `CLICK_DRAG` one

Blender's own "Pie Menu on Drag" preference (`params.pie_value`, `blender_default.py`) does not add a drag item
next to the key's action: it **changes the action from `PRESS` to `CLICK`** and adds the pie on `CLICK_DRAG`
(Z: `CLICK` = toggle shading, `CLICK_DRAG` = shading pie; also `` ` ``, Tab, I). A `PRESS` item fires as soon as the
key goes down, before Blender can tell a tap from a drag, so a `CLICK_DRAG` item of ours next to Blender's `PRESS`
item would never get the event (Quick Favorites or the context menu would already be open). Almost every useful
key is bound on `PRESS`. So "tap keeps the key's action" needs one of:

- **(a) a tap-or-drag operator of ours on `PRESS`** (add-on keyconfig): it waits; on release without moving it
  runs the key's own action (e.g. `wm.call_menu(name="SCREEN_MT_user_menu")`), on a drag past Blender's drag
  threshold it opens the pie. Native menus and pie; the key's action is re-issued by us. Needs a GUI check that the
  add-on item wins over the default one (add-on keymap items are matched first [unverified]) and that a re-issued
  menu behaves exactly like Blender's.
- **(b) a key with no `PRESS` action in Object Mode**: the pie on `CLICK_DRAG` alone, tap does nothing (or
  whatever we choose); zero interference.

## Finding 2 — the keys in Object Mode (Blender 5.2.2 defaults, left-click select)

## Options

1. **Right-mouse drag** (option (a) on RMB): right-click = the context menu with our selection entries (ADR 0013),
   right-drag = the pie. One button for both routes, no keyboard, Fusion's and Maya's habit. Cost: we re-issue the
   context menu on tap; left-select keymap only (with right-click select the preference must fall back to a key).
2. **Q drag** (option (a) on Q): tap = Quick Favorites, drag = pie; the conventional add-on key, but HardOps and
   MACHIN3tools take Q on `PRESS` and would hide our drag (users of both must rebind one).
3. **E drag or D drag** (option (b)): no Blender action to preserve, simplest and safest; D clashes with BoxCutter's
   pie, E with nothing in Object Mode (and E is under the left hand next to W/Q).
4. A dedicated tap key (E or D on `PRESS`), as HardOps/MACHIN3 do: simplest; loses nothing in Blender; no drag
   gesture.

**Recommendation:** option 1 (right-mouse drag) as the default, plus **E drag** (option 3) as a keyboard route
for users of right-click select or of a tablet; both rebindable in the add-on keyconfig. Before building: a GUI
check that an add-on `PRESS` item on RMB/Q wins over Blender's and that a re-issued context menu behaves like the
native one (position, last-used item). The maintainer decides.
